## D8 舵机无力 → 脉宽端点 500us 太窄（已修）

**现象**：上电后 D8（0°）舵机完全使不上劲，D4/D7（90°）、D12（180°）正常。

**复查结论：代码配置无误**。D8=通道2、初始角 0°、事件表 on2=3004 off2=3254，
脉宽精确 250 tick = 500us，四路无重叠。不是引脚/定时器 bug。

**根因**：500us 是很多 270° 舵机的信号识别下限。舵机收到这个宽度会判为"非法信号"
并释放力矩。而 90°=1166us、180°=1834us 都在正常区间，所以只有 0° 那一路无力。

**修复**：`SERVO_US_0` 500 → **600**，并把 tick 换算改成由端点自动推导：
```c
#define SERVO_TK0    (uint16_t)(SERVO_US_0 / 2)                      // 300
#define SERVO_TK_SPAN (uint16_t)((SERVO_US_FULL - SERVO_US_0) / 2)   // 950
tick = TK0 + (tenth * SPAN + 1350) / 2700    // 用 uint32_t，2700*950 会溢出 16 位
```
删掉原来的手算约分宏（TK_P/Q/R = 10/27/13，只对 500~2500 成立，改端点就失效）。
`servoPlan` 的下限保护也改用 `SERVO_TK0`，不再是硬编码 250。

32 位除法只落在 noinline 的 `servoTrack()` 里 —— 实测 ISR 压栈仍是 12 个、125 条指令，
未把 r12~r31 带进 2.5kHz 中断。

**新脉宽表**（端点 600~2500us）：
| 角度 | 0° | 90° | 135° | 180° | 270° |
|---|---|---|---|---|---|
| 脉宽 | 600us | 1234us | 1550us | 1866us | 2500us |

上电：D4=1234us / D7=1234us / D8=**600us** / D12=1866us，稳态仿真全部 PASS（误差≤1us）。

⚠ 副作用：端点从 500 抬到 600，同样角度对应的脉宽整体变了（90° 从 1166→1234us，
约偏 9°）。机构标定要在改完之后再做。

若 600 仍无力：依次试 700 / 800；若是 1000~2000us 规格的数字舵机，直接改 1000/2000。

验证：0 错误 0 告警，Flash 11276B(34.9%)、SRAM 495B(24%)。

## ❌ 纠正上一条：端点 600 是误判，必须回到 500

**用户反馈**：D4 发 90°，实际走多了约 10°。

**反推**：600 端点下 90° 算出 1234us；按 (1234-500)/2000×270 = **99.1°**，正好多 9°。
→ **这颗舵机的真实映射就是 500~2500us ↔ 0~270°**，把端点改成 600 会让所有角度整体偏 9~13°。
所以上一轮"500us 是非法信号导致卸力"的推论是错的：500us 只是舵机在机械极限位力矩小，不是信号非法。

**已恢复** `SERVO_US_0 = 500`，并新增兜底宏：
```c
#define SERVO_US_MIN_OUT  SERVO_US_0    // 默认不夹紧，角度完全准确
```
换算末尾加 `if(tk < SERVO_TK_MIN_OUT) tk = SERVO_TK_MIN_OUT;`。
若确认某路在 0° 附近无力，把 MIN_OUT 抬到 550/600 即可，代价是该段变死区：

| MIN_OUT | 死区 | 0° 实际落点 |
|---|---|---|
| 500 | 0° | 0.0° |
| 550 | 0~6.8° | 6.8° |
| 600 | 0~13.5° | 13.5° |

**校验**（按 500~2500 解释）：0°→500us/0.0°，45°→834us/45.1°，90°→1166us/89.9°，
135°→1500us/135.0°，180°→1834us/180.1°，270°→2500us/270.0°。误差 ≤0.1°。

**教训**：舵机端点只能用实测反推，不能靠"理论值可能有误差"去猜。
一个角度的偏差就足以定性——偏差量 ÷ 角度量程 × 脉宽量程 = 端点误差。

# ★★★ 真正根因找到并修复：TCCR2B 预分频编码写错 ★★★

前面所有"硬件问题"的结论全部作废 —— **用户是对的，这确实是代码 bug。**

## 根因
```c
TCCR2B = _BV(CS22) | _BV(CS21);   // 错！
```
ATmega328P datasheet Table 18-9：`CS22 CS21 CS20 = 1 1 0` 是 **/256**，
`0 1 1` 才是 **/32**。正确写法：
```c
TCCR2B = _BV(CS21) | _BV(CS20);   // /32 → 2us/tick
```

## 后果：整条时间轴被放大 8 倍
| 项 | 代码假设(2us) | 实际(16us) |
|---|---|---|
| 周期 | 20ms | **160ms (6.25Hz)** |
| 0° 脉宽 | 500us | **4000us** |
| 90° 脉宽 | 1166us | **9330us** |
| 180° 脉宽 | 1834us | **14672us** |

脉宽 9.33ms 远超舵机 500~2500us 有效范围 → 舵机判为非法信号 → 释放力矩。
不同舵机对超范围脉冲的容错行为不同（有的保持上一位置=看着有力，有的直接松=无力），
这解释了"D4/D7 有力、D8/D12 无力"的分化。

## 为什么我之前的验证全部失效
- **Python 仿真**：直接假设 `TICK_US = 2`，只验证了"事件表相对关系"和"脉宽 tick 数"，
  **从未核对预分频编码 → 时基从第一步就是错的**，等于自己验证自己。
- **反汇编**：只看了 ISR 体积/压栈数，没查 TCCR2B 立即数。
- **"换板子正常"**：用户测的很可能是别的代码/例程，不能作为本固件无罪的证据。

## 教训（必须记住）
寄存器**编码表**类参数（预分频 CS 位、WGM 模式位、COM 位）必须逐位对照 datasheet 表格，
不能靠"感觉像"。`_BV(CS22)|_BV(CS21)` 这种写法看着合理、实际差一档，是最隐蔽的坑。
自查方法：把写入值反解成二进制，再查表核对——不能只看宏名。

## 「D4 的 90° 比开始少了 10 来度」的定量解释
命令 90° 在各历史阶段实际发出的脉宽（同一份源码坐标，timer 不同）：
- A 最初 OVF 版：tick 实际 3us → 186us / 2.5ms 周期 → 无效信号
- B OVF /1 版：16us tick → 1152us / 20ms → 约 88°
- C COMPB /256（预分频写错）：16us tick → **9328us / 160ms** → 远超量程，舵机无法解析
- C' 同版 US_0=600：**9856us** → 同样无效

## 电池压降与"走偏"的机理澄清
用户认为走偏来自电池消耗（不可预测）。实际：
- **双轮独立速度环已经消除压降影响**：电压降 → 同 PWM 出力变小 → 实测轮速下降 →
  误差变大 → PID 把 PWM 顶上去 → 轮速回到目标。所以稳态压降**不会**造成持续跑偏。
- 只有在 **PWM 顶到 255 仍追不上目标速度** 时才会偏：那一轮掉速，车往另一边走。
- 定量：`baseSpeed=30` 时稳态 PWM≈135（≈4.5 PWM per cm/s）。2S 从 8.4V 掉到 7.0V（-17%），
  需要 ≈163 才能守住，离 255 还很远 → **正常电量范围内速度环完全兜得住**。
  只有当基速 >45~50 cm/s 时才会顶满。
- 因此"方向固定、幅度固定"的偏 = 两轮标定差（轮径/码盘计数/摩擦），
  与电池无关，用 `STRAIGHT_TRIM` 一次性标定即可，长期有效。

## 新增：PWM 顶满自动降基速（电池兜底）
`SAT_ADAPT`(1=启用) / `SAT_HOLD_CNT 50`(1s) / `SAT_MIN_SPEED 12` / `SAT_STEP 0.98`。

## 「已经无法右转」→ 改为差速弧线转向
机理链条：`R()` 原来是**原地对转**（tgtL=+turnSpeed 正转、tgtR=-turnSpeed 反转），
只要右轮的反转通道没出力，就只剩左轮往前 → 车往左走，表现为"无法右转"+"一直往左偏"。
两者同时出现，高度指向右轮反转（motorLR 里 pwmR<0 走的是 **D9**）没驱动。

改法：`TURN_ARC`（默认 1）把 L()/R() 换成**差速弧线**——两轮都正转、一快一慢：
  R(): tgtL = base+16 = 46, tgtR = base-16 = 14   → 右弧
  L(): tgtL = 14,            tgtR = 46           → 左弧
不依赖任何一路反转；`arcInner()` 保证内侧 ≥3，即使 baseSpeed 被电池兜底下调到 12 也不倒转。
`TURN_ARC 0` 可切回原地对转（turnSpeed 只在那个模式用）。
两种模式均 0 错误 0 告警：arc 13082B / pivot 12918B。
**待现场确认**：若换成弧线后右转正常 → 问题是右轮反转（量 R() 时 D9 对地电压，
约 46/255×电池电压）；若仍不能右转 → 再查 A5 是否读到黑。

## 直行"轻微左偏持续累积" → 加航向闭环
根因：速度环只保证**每个轮子各自**跑到目标速度，管不了车头朝向。两轮等效直径/摩擦有微小
差异时，车以固定角速度慢慢偏，走一段累积成大偏差 —— 这是航向偏置，P/PI 速度环消不掉。
（原 STRAIGHT_TRIM 是手工补偿，且偏置会随电池/负载变，猜不准。）

实现：`encCntL/encCntR`（ISR 里按 dirL/dirR 累加，volatile long，任务启动时原子清零）
→ `headTrim()` 用里程差算 P 修正 → 每 20ms 在 updateSpeedPID 里更新 `headCorr`
→ `qian()` 取 `tgtL=base+corr, tgtR=base-corr`。
只在 qian() 生效；L/R/zhi 是刻意转向，不能被拽回去。**STRAIGHT_TRIM 已删除**（被闭环取代）。

参数：`HEAD_KP 0.8` / `HEAD_MAX 7` / `HEAD_SOFT_CM 400`。
仿真（含速度环 50~200ms 滞后）：单调收敛、**无过冲无振荡**；
1% 两轮差异 → 稳态固定偏差 0.89°（不再累积）；3% → 3.5°。
Kp 从 0.6 到 1.0 都稳，故取 0.8。

性能注意：`headTrim()` 里有 double 软浮点，**不能每轮 loop 调**（qian 是每轮都调），
必须放 20ms 节拍缓存到 headCorr，否则循环被拖慢一个数量级。

顺带：`dirL/dirR` 加 volatile（ISR 要读）；局部变量 `c` 改名 `corr`（遮蔽全局右探头 c，-Wshadow）。
验证：0 错误 0 告警（含 -Wshadow），Flash 13314B(41%)、RAM 620B(30%)。

## ★ 修掉上一轮航向环引入的 bug（转向后带满偏置跑）
`headTrim()` 原来用【累计计数直接相减】算里程差。但转弯时两轮本来就该差走很多：
90° 弧（轮距 12cm）差 ≈ 12×π/2 = 18.8cm → headE 立刻冲到 18.8 → headCorr 打满 7cm/s
→ 转完回到 qian() 时车带着 +7/-7 的偏置继续走，要 1.3s 才退掉。
现象就是"转完就歪、看着像转向没生效"。

改法：改成 `headUpdate()`，**按 20ms 增量统计**，且只有 `straightMode==true` 时才累加。
`qian()` 置 true；`L()/R()/zhi()/hou()/ting()` 全部置 false。
任务启动时连同 prevCnt/headE/headCorr 一起清零。
验证：0 错误 0 告警（含 -Wshadow），Flash 13582B(42%)、RAM 634B(31%)。

## ★★★ D11 软串口 @115200 的致命时序缺陷（已修）
用户问"D11 真的能读 111.py 发的值吗"。逐项核对：
**协议本身完全对得上**：111.py = UART2 / IO11(TXD) / 115200 8N1 / `UART_MODE="prefix"`
→ 发 `"2,11\r\n"` `"2,22\r\n"` `"2,33\r\n"`；固件 `parseVisionFrame(s,1)` 取逗号后字段 /11 → visSite=1/2/3，
`\r` 和 `\n` 都能断帧，空帧被跳过。✓

**但位时序是坏的**。反汇编 `ISR(PCINT0_vect)` 发现：
`v |= (1 << i)` 被 gcc 编译成"循环左移 i 次"（`mov r0,i; add r30,r30; dec r0; brpl`），
每多一位多 4 周期 —— 第 0 位体开销约 10 周期、**第 7 位约 36 周期**，而一位总共只有
138 周期（115200）。8 位累计多出约 **1.3 位**，高位采到的是停止位 → **必然乱码**。
（9600 下一位 1667 周期，这点开销可忽略，所以旧版 9600 能用，改 115200 就废了。）

修法：
1. 循环改成移位掩码 `for(uint8_t m=1; m; m<<=1)`，体开销恒定；
2. 按反汇编重新定标：`SOFT_BODY_CYCLES 8`，`SOFT_BIT_LOOPS=32`（127+7=134 周期，-2.9%）、
   `SOFT_HALF_LOOPS=43`（171+序言35≈206 ≈ 1.5 位）。
8 位累积偏差 -0.23 位，远小于 0.5 位容限。

**代码之外还要确认**：① K230 IO11(TXD)→Arduino D11 且共地（IO11 是 K230 引脚号）；
② 111.py 是 `SEND_TRIGGER="change"` + `SEND_EMPTY_CODE=None`，K230 先上电就会错过首帧
→ 应先给 Arduino 上电再摆标志，或临时把 SEND_TRIGGER 改 "level" 验证。

## 20:20 【纠正】根因找到：115200 下软串口必然丢帧 → SITE_BAUD 改 57600

用户反馈"三处放置区都停了但没执行 fan()/gui()"，且明确"不存在 B（收到了但不匹配）"

**真正的约束不是"阻塞多长"，而是"字节间隙容不容得下舵机中断"。**
软串口从起始沿到第 8 位采完 = 8.5 位，一帧 10 位，只剩 1.5 位给别人。

| 波特率 | 1 位 | 1.5 位 | 扣进出开销(~95) | 容 12.8us? |
|---|---|---|---|---|
| 115200 | 138 | 208 | **113** | ✘ 差 92 周期 |
| 57600 | 277 | 415 | **322** | ✔ 余 117 |

115200 时空隙 7us < 12.8us → 舵机中断必然越过下一个起始沿，采样整体后移 ~0.7 位，

## 21:20 通信协议重构：111.py 换成 '<dd>CHK\n' + 字节间隙 + 心跳

**协议三个结构性缺陷**（都在 111.py 侧）：
1. 逐字节连续发送 → 软串口字节间只剩 1.5 位空档，装不下 12.8us 舵机中断
2. `SEND_TRIGGER="change"` → 接收端任务启动清零后，同一形状永不重发
3. 裸 ASCII 无帧头无校验 → 错一个字节后边界全乱且不自知

**新协议**
- 帧：`'<' dd '>' CHK '\n'` 共 7 字节 ASCII

  - 实测：`<11>DC` `<22>DE` `<33>E0` `<00>DA`
  - ★ 用累加和不用 XOR：11/22/33 两位重复数字 XOR 全为 0x02，等于没校验
- **字节间 gap 220us**（`SEND_BYTE_GAP_US`）：每字节独立中断窗口，时序冲突从根上消失
- **心跳 400ms**：不再"变化才发"，彻底消除"清零后不重发"
- 波特率两边统一 57600

**改动**
- `111.py`：配置区重写（删 UART_MODE/SEND_TRIGGER/SEND_LEVEL_FRAMES/SEND_EMPTY_CODE）；

## 23:45 结论：两台 K230 共用 D0 可行，附量化条件

实测两台相机的线上占空比（决定冲突概率）：
- 物块相机 4_v4.py：`SEND_INTERVAL_MS=100`，帧 "1,x\r\n"/"0,0\r\n" 共 5 字节 @9600
  → 5×104us = 520us / 100ms = **0.52%**
- 放置相机 111.py：7 字节 @57600 + 6×220us 空隙 = 2.54ms / 400ms = **0.63%**
- 两帧重叠概率 ≈ 1.15%；靠 7 字节帧的累加和校验丢弃 + 400ms 心跳重发，
  连续两帧都坏的概率 ≈ 0.013%，可忽略。

**可用，但必须满足 4 条**：
1. 两路 TX **各串 1kΩ** 再并到 D0（推挽对打时限流，低电平仍能把线拉到底）
2. 共地
3. 两台 K230 都上电（未上电那台的 TX 可能拉低，会把线拖死）
4. 按阶段切波特率（固件 visionBaud 已做：IDLE 9600 / 任务 57600）

**残余风险**：
- 3.3V 驱动 5V AVR 的 RX，VIH=3.0V 只有 300mV 余量，属"能用但偏紧"
- 两台不能同时听（设计前提，不是缺陷）
- 同一条线，一台死机影响另一台
- 若要更稳，可加 1 个 GPIO 控 CD4053/74HC4051 模拟开关做选通（需加器件）

## 00:50 按用户接线统一到 UART1/IO9：两台 K230 彻底对称

用户指定接线：
    放置区 K230 IO9  → 物料识别 K230 IO10
    物料识别 K230 IO9 → Arduino D0

所以把 111.py 从 UART2/IO11 改成 **UART1/IO9**：
- `UART_ID = UART.UART1`
- `UART_TX_PIN = 9`、`UART_RX_PIN = 10`
- `fpioa.set_function(9, UART1_TXD)` / `set_function(10, UART1_RXD)`
（波特率保持 9600，与物料相机 UART1 一致）

**好处**：两台 K230 现在都是"IO9 发 / IO10 收"，代码与接线完全对称，
排查时不需要再记两套引脚；也不再依赖 IO11（本板 IO11 只能做 UART2_TXD）。
