### 本轮修掉的致命 bug（多 Agent 审查 + 亲自验证）
1. **判区数学上不可能触发（P0）**：`if(fabs(delta)<JUMP_DELTA_CM){jumpCnt=0;return;}` + `JUMP_CONFIRM=2` 要求"连续两帧同向 Δ≥8cm"。但物理跳变是单帧一次性的，下一帧 Δ 很小 → 计数立刻清零 → `boxIdx` 永远停在 1，`f=2/3` 时车一路跑到丢线停死。**改为"边沿 + 时间锁 JUMP_LOCK_MS=200"**，并要求"变远/变近"成对出现。
2. **`stopLocked` 无解锁路径**：单帧 <5cm 就锁死，ST_LINE 期间无人清 → 一次多径反射就永久停死。加 `TOO_CLOSE_CONFIRM=3` + 距离恢复立即解锁。
3. **无任务超时**：任一阶段卡住只能断电。加 `TASK_TIMEOUT_MS=40000` 兜底回 IDLE。
4. **幽灵任务 / 永久空闲**：`qTaskLast` 在非 IDLE 阶段也被写 → 物体还在也永不启动；超时清零又导致同一物体重复取件。改为 `taskArm` + "先消失再出现"。
5. **第二个任务盒号错位**：`boxIdx` 在新任务清零，但 ST_LEAVE 后车停在上一个盒旁并不回起点 → 每次错一格。改为**跨任务保留绝对盒号**。
6. **视觉越权**：`zone = qSiteLast>0 ? qSiteLast : boxIdx` 让相机远远看到标签就恒等 → 原地投放。改为"已进过盒子 + 连续 3 帧一致"才采信。
7. **`dt` 无钳制**：软串口 1ms/字节阻塞会让 iTerm 一步冲高。加 `if(dt>0.05) dt=0.05`。
8. **`prevDist` 冻结**：无回波期间不复位基准，恢复瞬间拿几十帧前的值算差 → 假跳变。连续 5 帧无效即作废基准。
9. `ST_PICK_FWD` 到点后漏网一拍（落到循迹逻辑）→ 改为在 `move_tai` 内就地切换。
10. `echoReady` 读改写无保护、软串口环 8→16 + 溢出标志 + 起始位复核。

## 双 K230 真实分工确认（关键纠正）

用户澄清：**两个脚本不是"发错了一个"，而是分工不同**：
- `4_识别并串口上报v4.py` → **识别物块**：UART1 / IO9(TXD) → D0，**9600**，发 `1,1`/`1,2`/`1,3`，无目标 `0,0`，每 100ms 重发
- `111.py` → **识别放置区**（靠标志的几何形状区分区域）：UART2 / IO11(TXD) → D11，**115200**，发 `2,11`/`2,22`/`2,33`（圆形/三角形/正方形标志），`SEND_TRIGGER="change"` 变化才发、消失不发

**固件已按双路重构**：
- `VISION_BAUD 9600`（D0 硬件串口）+ `SITE_BAUD 115200`（D11 软串口）
- `parseVisionFrame(s, fromSite)`：D0 → visTask（1/2/3）；D11 → 11/22/33 归一成区域 1/2/3 → visSite
- `zone = (siteHit>=SITE_CONFIRM) ? qSiteLast : boxIdx`，siteHit 按**新帧**（visSiteMs 变化）计票
- 超时：`VISION_TIMEOUT_MS 1200`（物块相机重发）/ `SITE_TIMEOUT_MS 8000`（放置区"变化才发"，只作防挂死）

**115200 软串口的技术处理**（这是本次最硬的一点）：
- 一位 = F_CPU/SITE_BAUD = 139 周期 @16MHz，`micros()` 分辨率 4us 完全不够
- 改用 `_delay_loop_2`（4n-1 周期，16 位计数，9600 也够）+ **采样期间全程关中断**（ISR 天然关闭，绝不 sei()），否则 Timer2 每 16us 的舵机中断会把每位推长
- 延时宏按 `F_CPU/SITE_BAUD` 自动推导，改波特率只改一个宏
- 代价：每字节阻塞约 78us；放置区相机"变化才发"帧极少，实际影响可忽略
- ⚠ 115200 是 AVR 软串口极限（139 周期里要容纳 0~2.5us 的中断响应延迟）。若实测误码，把 111.py 的 `UART_BAUDRATE` 与 `SITE_BAUD` 同改 9600 即可，代码无需其它改动

验证：0 错误 0 告警，Flash 10956B(34%)、SRAM 492B(24%)，1268 行。

## 交换两个 K230 的 TX 接线（D0 ↔ D11）

交换后角色对调，且在技术上整体变好：
| 相机 | 脚本 | 引脚 | 波特率 | 串口类型 |
|---|---|---|---|---|
| 放置区 | 111.py | **D0** | **115200** | 硬件串口（零负担） |
| 物块 | 4_v4.py | **D11** | **9600** | 软串口（容错大） |

**固件改动**：
- `BAUD_SITE 115200`（D0）/ `BAUD_TASK 9600`（D11），`Serial.begin(BAUD_SITE)`
- `parseVisionFrame(s, fromSoft)` 分支对调：fromSoft=1（D11）→ visTask 物块；fromSoft=0（D0）→ visSite 放置区
- 软串口成帧函数改名 `pollSoftVision`（现在读物块相机）
- 延时宏改按 `BAUD_TASK` 推导：9600 → 1667 周期/位，`SOFT_BIT_LOOPS=417`、`SOFT_HALF_LOOPS=625`

**关键收益与代价**：
- 115200 交给硬件串口 → 彻底摆脱"AVR 软串口极限"（原来 8.68µs/位要关中断，舵机抖 78µs）
- 9600 软串口位宽 104µs，**改为允许 sei() 嵌套**：Timer2 的 2.5µs 延迟只占 2.4%，逐位累积约 19% 位宽（<50% 容限），换来舵机脉冲不被拉长 1ms（否则约 90° 抖动）
- 反过来若在 9600 下继续关中断，每字节 1.04ms 会直接把舵机脉冲拉长 1ms —— 所以这一步 `sei()` 是必须的，不是可选项

验证：0 错误 0 告警，Flash 10958B(34%)、SRAM 492B(24%)。

**后续：用户决定不交换接线，已全部回滚**到原接法 —— D0（硬件串口 9600）= 物块相机 4_v4.py；D11（软串口 115200）= 放置区相机 111.py。软串口恢复"全程关中断"（115200 下不能嵌套），每字节阻塞 78µs、舵机脉宽约 7° 抖动，因放置区相机"变化才发"故可忽略。
⚠ 遗留风险：115200 是 AVR 软串口物理极限。若实测放置区数据丢失/乱码，最省事解法是把 `111.py` 的 `UART_BAUDRATE` 与固件 `SITE_BAUD` 同改 9600，延时宏会自动重算，其它代码不动。

## 判区改回「17cm 停车 + 读放置区相机」（用户要求，5cm 急停保留）

**新流程**：
```
ST_LINE   巡线 + 超声波测距
            测距 ≤17cm 连续 3 样本(60ms) → 停车 + ST_DROP
ST_DROP   ting() → 停稳 150ms → 读 visSite
            visSite == f   → fan(r)+gui(r) 投放，dropDone=true
            visSite != f   → 不投放
            等不到相机(800ms) → 当作不是目标
          → 无论哪种，都进 ST_LEAVE
ST_LEAVE  qian() 前进，直到测距 > LEAVE_CLEAR_CM(22cm) 或超时 2s
            dropDone → ST_IDLE（任务完成）
            否则     → ST_LINE（继续找下一个盒）
```

**删除**：`updateBoxByJump()` 整套间隙突变计数（`boxIdx/inBox/prevDist/jumpedOut/jumpLockMs/nearCnt/voidCnt`）、`JUMP_DELTA_CM/NEAR_CM/NEAR_CONFIRM/BOX_MAX/SITE_CONFIRM`、`qSiteLast/siteHit`、`LEAVE_MS`。代码 1268→1161 行。

**5cm 急停保留**：`EMERG_CM=5.0` + 连续 3 样本，优先级高于 17cm 到站；停车但不进投放流程。锁满 `EMERG_UNLOCK_MS=3s` → 强制放行 + `EMERG_BYPASS_MS=1.5s` 脱困窗口（否则会"放行 40ms 立刻再停"原地抽搐）。

**关键设计**：离开用「测距变远(>22cm)」而不是固定时长 —— 盒宽/车速都会变，固定时长要么没走出去（刚回巡线又停），要么一下跨过两个盒（漏掉目标）。

⚠ 踩坑记录：用索引区间删除 `updateBoxByJump` 时误删了相邻的软串口段（`siteBuf/siteHead/siteTail/SOFT_RX_PIN`），编译报未声明，已补回。以后按索引删代码块要确认区间内只有目标内容。

验证：0 错误 0 告警，Flash 10450B(32%)、SRAM 475B(23%)。

## 270° 舵机角度接口 + 定时器资源全面核查（20:5x）

### 新增接口
`bool servoWrite(uint8_t pin, float deg)` —— 按【信号线 + 角度】控制，角度 0~270。
配套：`servoWriteCh(ch,deg)`（按通道）、`servoReached(pin)`（到位查询，替代 delay 做非阻塞编排）。
标定宏：`SERVO_DEG_FULL=270`、`SERVO_US_0=500`、`SERVO_US_FULL=2500`；换 180° 舵机只改 DEG_FULL + DEG_TENTH。

### 定时器资源结论（实测，不是估算）
- 向量占用：仅 3(PCINT0 软串口) / 4(PCINT1 编码器+ECHO) / 8(TIMER2_COMPB 舵机)，**互不冲突**；COMPA(7) 仍归 Tone.cpp。
- Timer0=millis+左电机PWM(D5/D6)，Timer1=右电机PWM(D9/D10)，不动。
- D3=PD3=OC2B、D11=PB3=OC2A，都是输入不做 PWM，`TCCR2A=0` 已关掉比较输出，安全。

### ★ 核心修复：舵机中断架构换掉（这是最大的一处）
旧方案用 TIMER2_OVF（16us 溢出），62.5kHz。**实测 ISR 182 条指令、无条件压栈 24 个寄存器（r12~r31）**，按指令周期算吃掉 **约 37% CPU** —— 根因是 `servoTrack()` 里的 32 位除法被内联。
改为 **TIMER2_COMPB 比较中断 + OCR2B 事件驱动**：
- 预分频 /32 → **2us/tick**，20ms = 10000 tick，分辨率从 16us 提升到 2us（0.27°/档）
- 每次中断把下一个事件排进 OCR2B（8 位计数器，单次最多 240 tick，更长就分段）
- 中断频率 62.5kHz → **约 2.5kHz（50 次/周期）**，CPU 降到 **约 2%**
- 换算改 16 位精确约分：`tick = 250 + (tenth*10 + 13)/27`（原 32 位 `tenth*2000/2700`）
- 只有角度真的变了才重算 tick（静止时 4 次比较就返回）

### 仿真抓到的真实 bug（肉眼看不出）
`ch0` 脉宽恒短 8us：周期收尾后 `distance=0` 必须抬到最小 4 tick 才能安全写 OCR2B，但 `on0` 仍写 0 → 被记在"逻辑时刻 4"。
修法：新增 `SERVO_ON0=4`，四路起点统一从 4 tick 开始，偏差归零。
验证方式：写 Python 时序仿真器复刻 TCNT2/OCR2B/ISR，6 组场景（全0°/全135°/全270°/各异/乱序/极值跳变）全部 PASS，中断约 50 次/周期。

### 其他修复
- 所有临界区 `noInterrupts()/interrupts()` → `SREG` 保存恢复（5 处：servoWrite/servoReached/readSpeedCmps/超声波×2）。原写法若从 ISR 或别的临界区调用会强行开中断。
- 文件头两处失真注释：① 写着"PCINT0 已空闲"，实际 D11 软串口在用；② 视觉协议写成"111.py→D0 115200"，实际 D0=物块9600 / D11=放置区115200。
- 删 `servoSet()`（改用角度接口）、`servoUs`、`svTick`、未使用的 `SERVO_TICK_US`。

### 唯一无法消除的抖动源（已在注释写明）
D11 软串口 115200 采样必须关中断 78us。若恰好落在某路高电平窗口内，该路脉宽被拉长 78us（270° 舵机约 10°）。放置区相机"变化才发"，几秒一帧，属偶发。

验证：0 错误 0 告警，Flash 11126B(34.5%)、SRAM 491B(24%)，1353 行。
