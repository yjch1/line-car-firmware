## 01:35 舵机动作改成 4 格环形队列（不再抢占）

用户反馈："舵机控制存在上一个还在执行就进入下一个"。

**根因**：`actStart()` 无条件 `qPins=0; qLen=0;` + 直接覆盖 actPins/actLen/actIdx，
即"新动作就地抢占"。已经下发的那一路舵机停半路，后续步骤永不执行。
典型：`qu()` 三步要 0.75~3s，车 1.5s 就出发；若 qu 没走完就判到站，
`fan()` 直接把 qu 顶掉 → 夹爪停在半开位置就去投放。`kai()` 也会顶掉 `gui()`。

**改成**（2.ino 3.5 节整体重写）
- 4 格环形队列：`qPins[4]/qDegs[4]/qLen[4]` + `qHead/qCnt`
- `actQueue()`：空闲且队列空 → 立即开始；否则排到队尾；满 4 个才丢弃（返回 false）
- `actBegin()`：只负责"开始一段"，不再清队列
- `actRun()`：当前动作最后一个舵机到位后才从队头取下一个；返回 `(qCnt==0)`
- `actDone()` = `!actBusy && qCnt==0`
- **四个入口 qu/fan/gui/kai 全部走 actQueue**，不再有 actStart
- RAM +17B（4×5 结构体 + 两个游标）

**仿真验证（5 组全 PASS）**

3. fan 走完但 gui 还在 → actDone 保持 false
4. 连发 6 个 → 前 5 个接受（1 执行 + 4 排队），第 6 个被拒
5. 空队列时 actRun 返回 true、不越界

## 01:45 ST_PICK_FWD 等取件动作完成才出发（pickDone）

用户反馈："执行 qu() 时还没执行完就进入下一个阶段了"。

**根因**：`fwdUntil` 在任务启动那一刻就算好了（`fwdUntil = millis() + START_FWD_MS`），
而 `qu()` 是三步舵机（0.75~3s）。1.5s 一到无条件切 ST_LINE，此时夹爪可能还在半路，
车已经在跑 —— 取件姿态和落点都偏。

**改法**
1. 新增 `bool pickDone`，任务启动时 `pickDone = false; fwdUntil = 0;`
2. `ST_PICK_FWD` 加第一关：
   ```c
   if(!pickDone) {
       ting();                                  // 取件期间车必须停稳
       if(!actDone() && (millis()-taskStartMs) < PICK_TIMEOUT_MS) return;
       pickDone = true;
       fwdUntil = millis() + START_FWD_MS;      // 取完才开始计时出发段
       bypassUntil = millis() + START_LOCK_MS;  // 超声波 4s 也从出发起算
   }
   ```
3. 新增 `#define PICK_TIMEOUT_MS 5000UL`：舵机卡死时 5s 强制放行，
   否则车永远停在起点只能等 40s 超时 —— 一个舵机拖垮一整场。

**为什么超声波锁定要跟着重设**：qu 若花 3s，原来从任务启动算的 4s 出发时只剩 1s，
等于出发段没有保护。

**时间线验证**
| qu 耗时 | 0~qu | qu~qu+1.5 | 之后 |
|---|---|---|---|
| 0.75s | 停车取件 | 直行 | 切 ST_LINE |
| 3.00s | 停车取件 | 直行 | 切 ST_LINE |
任何情况下 qu 未完成都不会切阶段、车也不动。

**行为变化**：原来是"边走边取"（省时间），现在是"停车取件 → 固定 1.5s 出发段"。
好处是出发段里程可标定（45cm @30cm/s），取件姿态也稳。

## 01:52 投放(fan)也加"动作没走完不走"的防线

用户反馈："fang() 运行时也有该问题"。

**核查结论**：`fan()` 全文件只有 `dropAct()` 一个调用点，而 `dropAct` 本来就有
`if(!match || actDone())`（actDone 含队列计数，fan 跑完时 gui 还排着 → 仍为 false）。
所以正常路径不会提前切。**但找到两条绕过它的路径**：

1. **40s 任务超时**：`if(stage != ST_IDLE && millis()-taskStartMs > TASK_TIMEOUT_MS)`
   无条件 `stage = ST_IDLE` —— 如果那一刻 fan 还在转，阶段已经变了，舵机还在原地慢慢转。
2. **ST_LEAVE 没有动作闸门**：只要 stage 变成 ST_LEAVE 就 `qian()` 开走，
   不管动作是否完成（"一边投放一边开走"）。

**改动（3 处）**
1. `dropAct()` 重写：
   - `!match` → 立刻走（不等动作，语义不变）
   - `match` → `!actDone()` 就 `ting()` 返回
   - 动作全完成后还要停 `DROP_TAIL_MS(300ms)` 才切 ST_LEAVE（`dropTailUntil` 只设一次）
2. `ST_LEAVE` 开头加最后防线：
   ```c
   if(!actDone()) { ting(); leaveStart = millis(); return; }
   ```
   leaveStart 每轮刷新 = 离开计时从"动作真的走完"才开始
3. 超时分支：`&& (actDone() || millis()-taskStartMs > TASK_TIMEOUT_MS + 3000UL)`
   —— 先等动作走完再收，但动作卡死时 3s 后照样强制回 IDLE

**为什么加 DROP_TAIL_MS**：`servoReached` 只代表"舵机角度到了"，夹爪张开/挡板下落
要把物块真正放下去还需要时间。原来一到位就开走，物块容易落在盒子边缘。

## 02:00 修回归：4s 起步锁定把 22cm 到站一起屏蔽了 → 超声波停车失效

**这是我上一手引入的回归**。当时把"收到 f 后锁 4s"直接写进 `bypassUntil`，
而 `STOP()` 里 `if(bypassUntil && millis() < bypassUntil) { cnt=emergCnt=0; return; }`
是**到站和急停一起屏蔽**。于是车在这 4 秒里直接冲过真正的盒子。

**改法：拆成两个互相独立的窗口**
| 变量 | 含义 | 屏蔽范围 |
|---|---|---|
| `bypassUntil` | 5cm 急停解锁后的脱困窗口 1.5s | 急停 **+** 到站（老行为，防止"放行→立刻再停"抽搐） |
| `startLockUntil` | 收到 f 后的起步锁定 4s | **只屏蔽 5cm 急停** |

- 任务启动：`startLockUntil = now + START_LOCK_MS; bypassUntil = 0;`
- `pickDone` 时：只重设 `startLockUntil`（不碰 bypassUntil）
- `STOP()`：
  ```c
  bool offBoth  = (bypassUntil && millis() < bypassUntil);
  bool offEmerg = offBoth || (startLockUntil && millis() < startLockUntil);
  if(offBoth)  cnt = 0;        // 每轮强制清零，防止窗口结束瞬间用旧票判停
  if(offEmerg) emergCnt = 0;
  到站计票条件： !offBoth && stage==ST_LINE && EMERG_CM < d <= STOP_CM
  急停计票条件： !offEmerg && d <= EMERG_CM
  ```

**真值表验证**
- 起步锁定内 20cm → **计票，会停车** ✓（修复点）
- 起步锁定内 4cm → 不急停（按要求保留）
- 脱困窗口内 → 两者都不计（老行为）
- 正常巡线 22cm → 停车；4cm → 急停
